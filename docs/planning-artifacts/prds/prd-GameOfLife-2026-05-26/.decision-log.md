## 2026-05-26 - Three-Phase Simulation Evaluation Model

**Decision:** Simulation engine uses three-phase evaluation per cycle:
1. **Phase 1 (Death):** Evaluate all "Die" rules → intermediate grid
2. **Phase 2 (Birth/Survive):** All organisms evaluate "Born" and "Survive" rules in parallel against the same intermediate grid → candidate claims
3. **Phase 3 (Conflict Resolution):** Apply Dominance values to resolve overlapping claims

**Rationale:** Parallel evaluation in Phase 2 prevents cascading dependency issues with Occupant Neighbor Count rules. If organisms evaluated sequentially (high Dominance first), lower-Dominance organisms would see newly born high-Dominance cells in their neighbor calculations, creating order-dependent behavior. Parallel evaluation ensures all organisms evaluate against the same grid state, making the simulation deterministic and predictable.

**Example:** If Red (Dominance 8) is born at cell (5,5), and Blue (Dominance 5) evaluates a rule "Born if Occupant Neighbor Count >= 1" at adjacent cell (6,5):
- **Sequential approach:** Blue would see Red at (5,5) during evaluation (order-dependent)
- **Parallel approach:** Blue evaluates against pre-birth state, doesn't see Red yet (deterministic)

Parallel evaluation produces consistent, understandable results regardless of Dominance ordering.

## 2026-06-23 - Architecture Conflict D Reconciliation: Unified Speed Scale

**Decision:** Reconciled the PRD with **Architecture Decision D** (one canonical speed scale + tick/render decoupling), recorded in `architecture.md` and propagated to RFC-002/005.

**Context:** Spec review found FR-4.2 (speed as ms/multiplier: 0.5×–3×) and FR-8.12 (speed as gen/sec: 1/5/10/30/60) were two inconsistent scales that did not actually map (only 10 gen/sec matched a FR-4.2 preset; the defaults disagreed; 60 gen/sec collides with the 60 FPS render frame). No RFC owned the runtime loop. Resolved with the product owner: one canonical **generations/second** scale, capped at 20 gen/sec, with the simulation tick rate decoupled from the render rate.

**Changes Made:**
- **FR-4.2** — presets rewritten to the gen/sec ladder **1, 2, 5, 10 (default), 20**; added an acceptance criterion that tick rate is independent of render frame rate.
- **FR-8.12** — unified to the **same** ladder (1, 2, 5, 10, 20; default 10); dropped the infeasible 30 & 60 gen/sec; reframed as "sets the starting speed of the FR-4.2 control" rather than a separate scale.

**Rationale:** gen/sec is concrete and intuitive for the target user; capping at 20 gen/sec guarantees ≤1 simulation step per render frame at every grid size (no spiral-of-death) and never over-promises against NFR-1.1 / Decision A. The decoupled accumulator loop (RAF renders ≤60 FPS; simulation advances one step per `msPerCycle`) is specified in RFC-002 §5 and RFC-005 Decision 5.

**Follow-up:** Re-run PRD validation. All four architecture conflicts (A–D) are now resolved.

## 2026-07-07 - Validation C-2 resolved: delete blocked across whole workspace; usage click-through

**Decision:** Resolved validation-report finding **C-2** — FR-1.4 only guarded the open grid, so deleting an organism referenced by *other* saved Battles was permitted and would silently corrupt them. ## 2026-07-07 - Validation H-5/H-6 resolved: cross-action precedence, owned by the simulation strategy

**Decision:** Resolved validation-report Highs **H-5/H-6** — the core competition mechanic was undefined: the 3-phase engine (FR-5.2 Die → FR-5.3 Born+Survive) *implied* "Die beats Survive" but never stated it, and Born-vs-Survive on an occupied cell had no tiebreak (the finding flagged this as contradicting UJ-1 "Blue holds its corner"). The MVP three-phase strategy makes the H-5/H-6 choices above; a **different, future strategy could preserve each organism's global rule order, or prioritize actions differently, by touching simulation logic alone** — organisms and the rules engine untouched.
