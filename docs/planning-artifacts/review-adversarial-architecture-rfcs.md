# Adversarial Review — Solution Architecture + RFC-001…008

**Date:** 2026-07-08
**Scope:** `docs/planning-artifacts/architecture.md` and all eight RFCs in `docs/planning-artifacts/rfcs/`
**Method:** Cynical cross-document review — every claim checked against the other documents, the cross-cutting decisions, and its own internal consistency.

Findings are ordered by severity. Section references are to the current drafts.

## Critical — design holes that will surface as bugs or rework

### 1. Persisted `organismType` rule patterns are battle-relative, but rules are workspace-shared
> ✅ **Resolved 2026-07-09 — architecture Decision E.** Rule patterns persist the stable library id; numeric refs are runtime-only, interned at evaluator-compile time (per-session cache). FR-1.4 delete block and the RFC-006 export closure/import assertion extended to rule references. Propagated to RFC-004/005/006/008 and PRD FR-1.4/1.7.
RFC-004 defines `OrganismRef` as *"the index into the dense organisms array built when a battle simulation starts"* (§2.1), and `OrganismTypeCondition` persists that numeric ref inside a rule pattern (`pattern: z.number().int()`, §2.4). But survival rules live **on the Organism**, and organisms are **workspace-shared across battles** (FR-7.15, RFC-001). The same persisted rule `organismType = 3` therefore targets a *different organism in every battle* — and is meaningless in a battle with fewer than four organisms. RFC-004 Risk 5's mitigation ("the battle remaps affected refs at edit time") makes it worse: the battle cannot remap a pattern stored inside a shared organism without corrupting that rule's meaning in every *other* battle using the organism. The §3.5 evaluator cache compounds it — evaluators are cached by `contentHash`, so the same compiled closure (with a baked-in battle-relative ref) would be reused across battles where the ref resolves differently. The pattern must store a stable organism **id** (translated to a numeric ref at compile time, per battle), or the "specific organism" property must be re-scoped. As specified, FR-2.5's Organism Type property is broken for any organism used in more than one battle.

### 2. Importing a single-battle file destroys the importer's settings — the exact thing RFC-006 Decision 6 promises it won't
> ✅ **Resolved 2026-07-09 — architecture Decision F.** Settings are device-local and out of the format entirely: no envelope (battle *or* workspace) carries settings, and `clearAll()` is data-only (battles + organisms — never `gol:settings`), so import cannot touch settings by construction. Clear All Data (FR-8.5) also preserves settings (product-confirmed). No PRD change needed — FR-8.3/8.5 were already scoped to battles and organisms. Propagated to RFC-006 (Decisions 1/2/4/5/6/7, Risk 4, Open Questions), RFC-001 (`clearAll` scope), RFC-008 (settings-preservation test). Also moots finding #13's settings↔`kind` coupling item.
RFC-006 Decision 5's `importWorkspace` runs `clearAll()` then writes settings only `if (envelope.settings)`. Decision 6 mandates that **battle** envelopes omit `settings`, explicitly so that *"importing a friend's battle must not overwrite the importer's theme, grid-lines, or default-speed preferences."* Follow the code path: battle import → `clearAll()` wipes `gol:settings` → no settings write → the importer's preferences are gone (reset to defaults at best). Decision 5 and Decision 6 directly contradict each other. The import flow needs to snapshot-and-restore current settings when the envelope lacks them (or `clearAll` must exclude settings on the battle-import path), and M8's "replaces the entire workspace" wording needs to say which behaviour is intended.

### 3. The `MAX_RELEVANT_AGE` clamp silently breaks `>` / `>=` age rules, and the age buffer type contradicts itself across three places
> ✅ **Resolved 2026-07-09 — Decision B.5 revised in place (no new decision letter).** Clamp is now `MAX_RELEVANT_AGE = max(7, maxAgeLiteral + 1)`, computed per battle at evaluator-compile time — saturated cells store one *above* the highest literal, so every operator (`eq/gt/lt/gte/lte/range`) stays correct against any literal ≤ maxLiteral. Canonical age-buffer type is **`Uint16Array`** (§3.4 and A.6 were already on Uint16; the two `Uint8Array` claims in §3.3/B.5 retired), and `NumericPattern` literals are now schema-bounded `.int().min(0).max(65534)` so `maxLiteral + 1` always fits Uint16 — this also closes finding #13's unbounded-age-literal item. Propagated to RFC-004 §2.4/§3.3/§3.4 and architecture Decision B.5.
RFC-004 §3.3 / Decision B.5 clamp stored age to *"the highest age literal any organism's rules reference."* If a rule says `age > 20` and the clamp is therefore 20, a cell's stored age saturates **at** 20 and `age > 20` is *never satisfiable* — the user's rule silently never fires. The clamp must be `maxLiteral + 1` (or the semantics documented). Separately: §3.3 and Decision B.5 both claim the clamp lets the age buffer "stay a `Uint8Array`", while §3.4's `Grid` declares `age: Uint16Array` and architecture A.6's memory math (144 KB at 200×120) is computed on Uint16. Three statements, two types — and the Uint8 claim is false anyway if any rule references an age literal above 255 (nothing in the Zod schema bounds it).

### 4. Import validation does not enforce the architecture's own invariants — H-9 grid sizes, cell bounds, and the hidden 255-organism cap
> ✅ **Resolved 2026-07-09 — architecture Decision G.** (G.1) `gridSize`/`gridDimensions` now validate against a single-sourced `EditableGridPresetSchema` (`{50×30} | {100×60}` literals — H-9 enforced at both boundaries; future presets ride the `formatVersion` chain). (G.2) `superRefine`s added: at rest, `gridState` dimensions must match `gridSize` and cell values must index into `organismIds`; on import, cells must lie within `gridDimensions` and duplicate coordinates are rejected. (G.3) The per-battle cap is **stated as 255** (type-derived from the dense encoding / `Uint8Array` occupant — product-confirmed over widening to Uint16): `organismIds.max(255)` at rest, ≤255 distinct organisms per battle on import, UI blocks the 256th; M6 clarified — the *library* is uncapped, one battle's roster is not. Also closes finding #13's `gridState`-missing-`.int()` item. Propagated to RFC-001, RFC-006, RFC-004 §3.4, architecture M6. No PRD change needed.
Decision A / H-9 restricts **persisted** grids to {50×30, 100×60}, yet `BattleSchema.gridSize` (RFC-001) and `gridDimensions` (RFC-006) are unconstrained ints — a hand-edited or future-app file with a persisted 200×120 (or 999×999) grid passes Zod, violating H-9 and the ≤180 KB undo-memory guarantee that depends on it. `PlacedCellSchema` bounds `x`/`y` only at `min(0)` and `assertReferentialClosure` checks organism ids only — nothing rejects cells outside `gridDimensions`, which the sparse→dense conversion will then write out of bounds. Also unstated anywhere: the dense encoding (`0..255`, RFC-001) and `occupant: Uint8Array` impose a hard **≤255 organisms per battle** cap, while M6 announces organism count is "uncapped." The real cap should be stated and enforced at the schema/UI boundary, not discovered as a typed-array overflow.

### 5. The organism-usage index can't be built from the interface it's specified against
> ✅ **Resolved 2026-07-09 — architecture Decision H.** "Used by a battle" = **placed** (≥1 cell on `initialGrid`), one definition everywhere (product-confirmed over roster-membership semantics). `BattleSummary` is now defined in RFC-001 — `{ id, name, gridSize, organismIds, updatedAt }` — and carries the placed `organismIds`, so the Decision 8 index builds from `list()` with zero grid deserialization. Persisted `organismIds` ≡ the placed set (schema-`superRefine`d; pruned at save with the E.2 remap), which also answers the pruning question and makes the cells-only envelope losslessly round-trippable with no format change; unpainted dropdown entries are RFC-005 session state that never persists or blocks deletion. Propagated to RFC-001, RFC-005 Decision 8, RFC-006 Decisions 4/5, architecture M7 + FR-1 traceability. No PRD change needed.
RFC-005 Decision 8 derives `organismId → battleId[]` from `battles.list()`, but RFC-001 defines `list()` as returning *"lightweight summaries for the Gallery"* (`BattleSummary[]`). No document says a summary carries `organismIds`; if it doesn't, `buildUsageIndex(data)` cannot be computed, and if the fallback is `listFull()`, every Library/Editor mount deserializes every full grid just to show a warning count. Either the `BattleSummary` contract must include `organismIds`, or the index needs another source. Compounding this, "referenced" is defined inconsistently: the saved-battle delete-block is roster-based (`battle.organismIds`), while the open-battle check is **placement**-based (`initialGrid` cells). An organism selected in a battle's roster but never painted blocks deletion via the saved battle but not via the open one — and no document specifies whether `organismIds` is pruned when the last cell of an organism is erased. FR-1.4's "highest-risk correctness claim" (RFC-008's words) sits on an unpinned definition.

## High — internal contradictions between accepted decisions and RFC text

### 6. RFC-002 contradicts Decision B about what rendering batches on — in its own text
> ✅ **Resolved 2026-07-09 — Decision B.2 revised: colour-state batching is the design.** The contradiction was resolved *toward* the Background's claim, because the doc set had already committed to it: M6's uncapping rationale ("reuse colours without adding render states") is only true under colour-keyed batching, RFC-007's `displayColor` is a pure function of `(colorToken, ageShade)`, its LUT arithmetic was already palette-keyed ("PALETTE entries in use × 8"), and its `hex` is the full-saturation age-cap colour — so non-aging organisms key as `(token, 7)`. Batch key is now `(colorToken, ageShade)` with a per-battle `OrganismRef → fill-group` LUT; worst case **≤ 20 × 8 = 160 fill groups, palette-derived and independent of organism count** — a true bound again under M6 and Decision G.3's 255-per-battle roster (organism-keyed would have been 2,040). Propagated to architecture Decision B heading + B.2, RFC-002 Background + §3 (prose, code, anchor), RFC-007 Links + Decision 4. RFC-002's other hygiene defects (finding #14) remain open.
RFC-002's Background states *"Rendering batches by **colour**, so the bound is the palette size, not organism count — organisms can exceed 20 by reusing colours without adding render states"* — while Decision B.2 and RFC-002 §3 (the actual design) batch **by organism × age-shade** with the bound derived from *organism* count (≤20 × 8 = 160 fill groups). Both cannot be true; under organism-keyed batching, two organisms sharing a colour are still two groups. And since M6 uncapped co-placed organism count (NFR-1.1's "20" is a baseline, not a limit), the "≤160 groups" worst case is no longer a bound at all — the batching claim needs restating against N organisms (or colour-keyed batching needs to actually be the design).

### 7. Three version axes, two incompatible migration conventions, no execution order
> ✅ **Resolved 2026-07-09 — architecture Decision I.** One pipeline, one convention, one owner: RFC-006's **source-keyed** `formatVersion` chain is the only migration machinery, running at exactly two boundaries (at-rest load, file import). Rule-schema changes and destructive palette-token changes bump `formatVersion` and land as steps in that chain; each step is one atomic function (internal order: structure → rules → palette tokens). RFC-004's target-keyed load-time pipeline is **retired** — `loadSurvivalRules` is now parse + assert (`schemaVersion` mismatch = corrupt, never a branch point); `PALETTE_VERSION` is a registry provenance stamp (additive changes need no migration at all). RFC-006 Alternative 5's claim is now normative rather than contradicted. Propagated to RFC-006 (Decision 3 + Alt 5), RFC-004 (§2.4 pipeline/example/principle 7/Risk 7/patterns table/Next Steps), RFC-007 (Links, Decision 1 migration-safety, Risk 2, Next Steps), RFC-001 (`schemaVersion` comment). No PRD impact.
The system now has `formatVersion` (envelope), `schemaVersion` (rules, per organism), and `PALETTE_VERSION` (colour tokens). RFC-006 keys migrations by **source** version (`MIGRATIONS[from]`, loop `from < CURRENT`); RFC-004 keys them by **target** version (`range(raw.schemaVersion + 1, CURRENT_VERSION)` → `migrations[v]`), and runs at organism load — while RFC-006 Alternative 5 asserts the rule-level version *"is migrated as part of the envelope step that touches organisms."* Which is it — rule migrations inside the envelope chain, or a second pipeline at organism load? In what order do palette migrations run relative to rule migrations when both fire? One convention, one execution order, one owner — currently there are two of each and no owner.

### 8. RFC-003's theme-switching mechanism likely doesn't deliver the claimed CSS-variable swap
> ✅ **Resolved 2026-07-09 — architecture Decision J.** RFC-003 Decision 2 rewritten: **one immutable `createTheme()` + an app-owned `--gol-*` CSS-variable token layer** (dedicated CSS file, per-`[data-theme]` blocks); a switch is a pure attribute flip — no React render, no Emotion work, no provider swap — so the <100ms/<16ms claim is now substantiated by construction. MUI's packaged `colorSchemes` was evaluated against the official docs and rejected for cause (product-confirmed): schemes vary palette only (our themes also differ in typography/radius/overrides) and are typed for `light`/`dark`, which two dark brand themes would have to squat. Accepted constraints documented (no JS colour math — derived shades become tokens; explicit `contrastText`; constant `palette.mode`). Bonus: the FOUC script now reads `gol:settings` instead of a stray `theme` key (single source of truth, RFC-006). This design satisfies NFR-8.2/8.4/8.5's ACs verbatim. Propagated to RFC-003 (Summary, Decisions 2–3, Risks 3/4) and the architecture tech-stack/traceability rows.
The RFC defines **two separate `createTheme()` objects** and says *"the `ThemeProvider` selects the active theme object based on the `data-theme` attribute."* Swapping the theme object passed to `ThemeProvider` is a React re-render through Emotion — precisely the runtime recomputation the CSS-variables argument claims to avoid. MUI v6's fast, attribute-driven switching works when both palettes are registered as `colorSchemes` of a **single** theme, with the switch being only the `data-theme` attribute flip. As written, the design and the <100 ms/no-FOUC rationale don't match; either restructure to one theme with two color schemes (noting `colorSchemes` differ from full themes — the Terminal's typography/shape/component overrides need a strategy), or re-justify the budget under a full provider swap.

### 9. RFC-004's canonical persisted-organism example still stores a raw hex colour
> ✅ **Resolved 2026-07-09 — propagation applied (no new decision; completes RFC-007 Next Step 3).** The §2.4 example's `"color": "#ff3b30"` is now `"colorToken": "coral-red"` (a real RFC-007 registry token) with a comment banning raw hexes. Swept every spec for other organism-level raw hexes: none remain — the only `color` hits are inside RFC-002's *rejected-alternative* illustration snippets (D3/PixiJS), which don't describe the persisted shape.
The §2.4 JSON example — the document's single authoritative illustration of the persisted shape — contains `"color": "#ff3b30"`. RFC-007 Decision 1 (and RFC-001's updated schema) made `colorToken` the stored value and explicitly banned raw hexes on organisms; RFC-007 Next Step 3 claims the token model was propagated. It wasn't propagated here, and this is the example implementers will copy.

## Medium — staleness, unproven claims, spec gaps

> ✅ **Resolved 2026-07-09 — all four items fixed in RFC-001.** (a) `build:standalone` is now plain `next build` with a `next.config.mjs` snippet showing `output: 'export'` gated on `NEXT_PUBLIC_MODE` (with a comment noting the `next export` command was removed in Next.js 14). (b) The repo diagram's `apps/web/pages/` → `app/` with the App Router routes, citing Cross-RFC Reconciliation #4. (c) `packages/test-utils` added to the diagram, matching architecture.md and RFC-008. (d) `turbo.json`'s `"pipeline"` → `"tasks"` (Turborepo 2.x), with a comment. Swept the whole spec set — no other `next export`/Pages-Router/`pipeline` remnants remain.
(a) `build:standalone` runs `next build && next export` — the `next export` command was removed in Next.js 14; the architecture doc itself says static export is `output: 'export'`. (b) The repo-structure diagram shows `apps/web/pages/` — Pages Router — while Cross-RFC Reconciliation #4 makes App Router canonical. (c) The structure omits `packages/test-utils`, which the architecture doc and RFC-008 both include. (d) `turbo.json` uses the `pipeline` key, renamed `tasks` in Turborepo 2.x. Individually minor; collectively the "oldest doc goes stale" failure mode the reconciliations were supposed to have fixed — it will mislead scaffolding stories.

### 11. The RAF accumulator has no clamp — Decision D's "no spiral-of-death" only holds in steady state
> ✅ **Resolved 2026-07-09 — clamp specified in Decision D.3 + RFC-002 §5.** `delta` is clamped to `msPerCycle` before entering the accumulator (`accumulator += Math.min(delta, msPerCycle)`): a suspended tab / long GC pause resumes with **at most one step** instead of a fast-forward burst; unkeepable time is *dropped* (D.4 graceful degradation), never banked — which also makes the single `if` safe against being "fixed" into a `while` (the accumulator can never hold more than one cycle). Propagated to architecture D.3 (dated note — the guarantee is no longer steady-state-only), RFC-002 §5 (prose + code), and RFC-005 Decision 5's summary line.
RFC-002 §5's loop adds raw `delta` to the accumulator. After a tab suspension or long GC pause, `delta` can be tens of seconds; the accumulator then drains at one step per frame, producing a multi-second fast-forward burst the user never asked for (and, if anyone "fixes" the single `if` into a `while`, an actual spiral). One line — clamp `delta` (or reset the accumulator on visibility change) — but it must be specified, since D.2 currently advertises the guarantee unconditionally.

### 12. RFC-006's quota argument is justified by the wrong storage shape
> ✅ **Resolved 2026-07-09 — dense-at-rest arithmetic written in.** Decision 7's monitoring bullet now derives the budget from the dense shape: ~12 KB JSON per mostly-empty dense 100×60 `gridState` (~24 KB pathological worst; ~6 KB at 50×30) → 50 battles ≈ 1.2 MB worst + ~200 organisms × ~2 KB rules ≈ 0.4 MB ≈ **1.6 MB total, about a third of a conservative 5 MB quota** (with a UTF-16 code-unit note so the headroom holds under the strictest metering). Decision 2's rationale corrected in the same pass — sparse cells are justified as small *share files* (wire-only), explicitly not as a quota argument. Conclusion unchanged, justification now true.
Decision 7 claims the NFR-7.2 target *"fits comfortably in 5–10 MB **with sparse cells**"* — but Decision 2 (and Cross-RFC Reconciliation #3) store battles **dense** at rest; sparse is wire-only. The conclusion probably survives (≈15–20 KB of JSON per dense 100×60 battle × 50 battles ≈ 1 MB), but the stated justification is false as written, and no dense-at-rest arithmetic appears anywhere. Show the real numbers or the meter/quota story rests on an argument that doesn't apply.

### 13. Schema laxity the documents' own rules say shouldn't exist
> ✅ **Resolved 2026-07-09 — last item closed; the other three were closed by earlier resolutions.** `OrganismSchema.dominance` now has `.int()` (RFC-001 — the Pydantic/SQL mirrors already enforced integer). Previously closed: the settings↔`kind` coupling is moot (Decision F removed `settings` from the envelope entirely); `gridState` values gained `.int()` + bounds/refinements (Decision G); `NumericCondition` literals are bounded `.int().min(0).max(65534)` (finding #3 / B.5 revision). Property-specific tightening of neighbour-count literals (0–8) remains editor-level UX by design, as noted in RFC-004 §2.4.
`WorkspaceExportSchema` doesn't tie `settings` presence to `kind` (a `battle` envelope with settings, or a `workspace` envelope without, both validate — Decision 6 says both are wrong). `OrganismSchema.dominance` lacks `.int()` (FR-2.2 is 1–100 integer; RFC-004's example says so). `gridState` cell values lack `.int()`. RFC-004's `NumericCondition` age literals are unbounded (feeds finding 3). Each is one line; together they mean the "validation at repository boundaries" story is weaker than advertised.

## Summary

| Severity | Count | Theme |
|---|---|---|
| Critical | 5 | Battle-relative refs in shared rules; settings-destroying import; age-clamp semantics; unenforced H-9/bounds invariants; unbuildable usage index |

| Medium | 7 | RFC-001 drift; accumulator clamp; quota rationale; schema laxity; RFC-002 hygiene; RFC-005 wiring; ratification/staleness |

The recurring failure mode is **decision propagation lag**: cross-cutting decisions (A, B, C, D, M5–M10) were made carefully, but the RFC bodies — especially RFC-001 and RFC-002 — retain pre-decision text alongside the post-decision corrections, and several "reconciled" claims (Decision 6 vs Decision 5; B.5 vs §3.4; batching-by-colour vs Decision B) contradict the very decisions they cite. Findings 1–5 should be resolved as new cross-cutting decisions before epics are derived; the rest are RFC edits.
